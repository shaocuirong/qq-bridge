# 会话成本：一轮一会话（docs/guides/SESSION_COST.md）

> 状态：✅ 新增（2026-10-16）。开关：`socialV2.context.freshSessionPerWake`（默认开）。
> 相关：控制台「二代仿真 → 上下文参数」里的「一轮一会话（省 token）」勾选框。

## 1. 问题：一个会话聊到底，成本随历史滚雪球

老做法是每个 QQ 会话只建**一个** DSH 会话，一直聊下去。每轮回复都要把
「人格提示词 + 整段聊天历史 + 之前所有工具调用与结果」重新发给模型一遍；
一轮回复里每个工具步骤（看未读、发消息、等消息…）又要重发一遍。

于是：

- **缓存热的时候**只是"便宜"，不是"免费"：实测一个群 3 小时里 47 个步骤，
  累计 `cacheHit` **302 万 token**、`cacheMiss` 2.05 万、输出 1.45 万。
- **缓存冷掉的时候（冷群最常见）**，这整段历史按 `cacheMiss` 计价。实测同一天的私聊会话里
  出现过两次完全冷启动的步骤：`miss=50,425 / hit=0`、`miss=53,418 / hit=0` ——
  同一个 prefix，命中价 ¥0.02/M、未命中价 ¥1/M，**差 50 倍**。
- **历史只增不减**：第 N 轮回复要重发前 N 轮的全部内容。所以单轮成本随"这个会话聊了多久"线性上涨，
  累计是平方级（每轮还要乘以该轮的工具步数）。说"指数爆炸"不准确，但"越聊越贵、没有上限"是真的。

## 2. 改法：每次回复都新开会话，上下文换成已读/未读快照

正常唤醒回合完成后，桥接程序自动确认已展示的连续消息水位，并维护有效唤醒配置；
不再投递「未完成回合收尾」的模型提醒，也不要求每轮调用 `qq_mark_read` / `qq_set_wake_config`。
新到与尚未展示的消息保留未读；失败、取消或暂停的回合不自动确认。模型主动设置的唤醒条件与
显式确认的水位继续保留，主动调整潜水配置时仍遵守工具的观察要求。仅为自动收尾无需等待五分钟。
旧配置 `maxWakeConfigReminders` 继续兼容读取，但不再产生提醒回合。

`freshSessionPerWake: true` 时，**每次唤醒/回复前先归档上一轮的 DSH 会话**，本轮从空历史开始：

```
QQ 消息 → 社交状态（未读队列 / 已读水位 / 记忆 / 令牌）
        → 提示词里的【本次消息快照】：未读消息 + 最近 N 条 + readThroughSeq + 自己刚说过的话
        → 新会话（空历史）→ 模型 → 回复
        → 下一轮：归档这个会话，再开一个空的
```

- **上下文没有丢**：模型需要的都在提示词里 —— 未读消息原文、最近若干条（含机器人自己刚发的）、
  已读水位（`readThroughSeq` / `modelSeenSeqs`，工具 `qq_get_unread_messages` / `qq_mark_read` 用的就是它）、
  轻量记忆（进行中的话题 / 想说未说的话 / 对群友的印象）、黑话表、表情库摘要。
  换新会话时这些**一律不重置**（只有会话映射被换掉），所以行为与原来一致。
- **成本变得可预期**：一次回复 ≈ 一条提示词 + 一条回复，跟你聊了多久、聊了多少条无关。
- 新会话模式下默认把快照给厚一点：`wakeRecentLimit` 4 → **10**、`wakeMaxChars` 6000 → **9000**
  （显式配置的值优先；要更省可以自己调小）。

### 不轮换的情况

| 场景 | 是否轮换 | 为什么 |
| --- | --- | --- |
| `reserved2` / `reserved` / `chat`（QQ 群、私聊） | ✅ | 就是本文要治的场景 |
| `closed-agent`（管理员运维会话） | ❌ | 那是多轮工具作业，连续上下文有意义 |
| `internal:`（黑话学习 / 研究会话） | ❌ | 不是聊天，是内部流水线 |
| 上一轮**还在生成**时 | 暂时不轮换 | 归档会连带停掉进行中的回合，把回复弄丢；等它结束后的下一次投递再轮换 |

## 3. 实测（本机、deepseek-flash 闲时价：命中 ¥0.02/M、未命中 ¥1/M、输出 ¥4/M）

| 会话 | 步数 | cacheMiss | cacheHit | 输出 | 折算成本（闲时 / 峰值×2） |
| --- | --- | --- | --- | --- | --- |
| 群 `1064849619`（老：一个会话聊到底） | 47 | 20,505 | 3,024,640 | 14,485 | ¥0.139 / ¥0.278 |
| 群 `1064849619`（新：轮换后 4 轮回复） | 4 | 50,514 | 157,056 | 1,879 | ¥0.061 / ¥0.122 |
| 私聊（老） | 14 | 30,228 | 706,176 | 3,471 | ¥0.058 / ¥0.117 |
| 私聊（新，一轮回复） | 1 | 1,759 | 48,384 | 333 | ¥0.004 / ¥0.008 |

读法：老会话的成本是"**随历史累积的一次性总额**"，每多聊一轮就多垫一段历史；
新会话的成本是"**每轮一条提示词的固定额**"，第 1 轮和第 20 轮基本一样（实测 4 轮报价总额 ¥0.061）。
冷群里历史越长，省得越多。

## 4. 代价与边界（别只看好处）

- **热聊场景不一定更省**：如果群很热闹、几秒一条，KV 缓存一直是热的，老做法按 `cacheHit`（¥0.02/M）
  摊那段共同前缀，单轮可能比新做法的"每轮一条冷提示词（¥1/M）"更便宜。
  新做法换来的是**上限**：不再随历史长度上涨。要不要开，取决于你更怕"贵"还是更怕"不可预测"。
  关掉即可回到老行为（`"freshSessionPerWake": false`）。
- **首字延迟略高**：每轮都要新建会话 + 挂 preset + selectModel（本机实测 1 秒上下），
  换来的是模型不用再读整段历史。冷群里整体反而更快。
- **DSH 里的会话数会随回复数线性增长**：旧会话被**归档**（列表里隐藏，仍可查/可恢复），
  不是删除。控制台有批量归档入口；磁盘占用 = 每轮一个只含一两轮事件的会话。
- **不影响**：未读/已读、唤醒调度、静默、限额、工具面、人格；`agentToken` 与 `bootstrapSent`
  在轮换时**刻意保留**（前者写在提示词里、换了就等于把 AI 手上的令牌作废；后者重置会多触发一次 bootstrap 唤醒）。

## 5. 怎么看它有没有生效

```powershell
# 当前是否开启（以及快照预算）
node -e "console.log(require('./config.json').socialV2.context)"

# 桥接日志里每次轮换都会留一行
Select-String -Path state/bridge.log -Pattern '\[fresh\]'

# 每个会话的实际用量（自算成本；价格表见 src/model-prices.js）
node -e "const fs=require('fs');const r=fs.readFileSync('state/token-usage.jsonl','utf8').trim().split(/\n/).map(l=>JSON.parse(l)).filter(x=>x.k==='turn');const m=new Map();for(const x of r){const e=m.get(x.sid)??{n:0,miss:0,hit:0,out:0,key:x.key};e.n++;e.miss+=x.b.cacheMiss;e.hit+=x.b.cacheHit;e.out+=x.b.output;m.set(x.sid,e)};for(const [sid,e] of m)console.log(sid.slice(0,20),e.key,'steps='+e.n,'miss='+e.miss,'hit='+e.hit,'out='+e.out)"
```

回归断言在 `scripts/test-fresh-session.mjs`（连续两次唤醒换会话且归档旧会话、轮换不动未读/已读/令牌、
关掉开关回到老行为、`closed-agent`/`internal:` 不轮换、回合在途不轮换、提示词里确实带快照）。

## 6. 唤醒自愈：别让一个会话永久静默（2026-10-16 线上故障记录）

**症状**：群里 @ 了没反应；只有某一个群在回，其它会话的消息全都只入库、不转发给 DSH。

**根因**：桥接把「这个会话有回合在跑」当作不能唤醒的依据（`isConversationBusyV2` 里的
`collectors` / `v2TurnStartAt` 标记），而那次回合的 `turn/end` 可能**永远收不到**：

- 桥接在回合进行中被重启时，重连快照里只剩 `turn/start`（`rebuildInFlightCollector` 会把它恢复成
  「仍在生成」）；如果那个回合其实早已结束，这个标记就永远挂着；
- 事件流断线，或轮换时 `events.forget(旧会话)` 让旧会话的 `turn/end` 再也收不到；
- DSH 侧回合被取消但没有发出结束事件。

标记一旦挂着，之后**每一次**唤醒都会进 `st.pendingWakeReasons` 暂存，而暂存原本**只在同一个会话的
`turn/end` 时补发** —— 没有 `turn/end`，积压的唤醒就再也没人处理：该会话从此永久静默。
当天为了上线改动多次重启桥接，把这个「偶发」放大成了「必现」。

**三层自愈**：

| 机制 | 配置 | 默认 | 作用 |
| --- | --- | --- | --- |
| 「生成中」租约 | `socialV2.wake.busyLeaseMs` | 5 分钟 | 标记超时且没有回合结束就强制解除。真还在跑也不丢：prompt 以 `queue` 模式入队，回合结束后自然会被处理 |
| 暂存唤醒兜底轮询 | 固定 60s（`sweepPendingWakeReasonsV2`） | — | 每分钟扫一遍：此刻不忙就把积压的唤醒重新排上；触发它的消息若已被处理（不在未读里）就丢弃，不复活旧唤醒 |
| 启动补投 | `socialV2.wake.startupCatchUpMs` | 30 分钟 | 重启后补一次唤醒（只补「最新一条未读还落在窗口内」的会话），否则「重启前 @ 了它」会一直没人回 |
| 恢复判据收紧 | — | 尾部 20 条 | `rebuildInFlightCollector` 只在「未结束的 `turn/start` 位于快照尾部 20 条内」时才恢复，避免把早已结束的老回合误判成在跑 |

**自查一个会话为什么不回复**：

```powershell
curl.exe -s "http://127.0.0.1:3100/api/socialV2/states?token=<token>"
# busy / busyReason 直接告诉你是哪个条件挡着（pendingWakeTimer / pendingWakeKeys /
# promptQueue / turn-in-flight），pendingWakeReasons 是积压的唤醒，turnStartedAgoMs 是标记挂了多久
```

日志关键字：`[fresh]`（轮换）、`兜底轮询：重新排上积压的唤醒`、`强制解除`、`启动补投`。
